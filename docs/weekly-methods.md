# Weekly artist landscape: method and limits

## Observation and playback

An ISO week starts **Monday 00:00 UTC** and ends at the next Monday 00:00 UTC, exclusive. ISO year 2026 has 53 weeks; W01 starts December 29, 2025 and W53 ends January 4, 2027. The version-3 manifest lists every ISO-week slot as `complete`, `partial`, or `missing`. A missing slot has no snapshot path. The main timeline shows only completed observations; for one or two weeks it uses explicit week buttons, then it becomes a draggable selector over completed observations. The separate **Live preview** button opens the partial week. Play advances only when the immediately next calendar week is also complete. It stops at a gap, partial week, or the last completed observation. It does not connect two nonadjacent weeks through an invented route. The initial position is the first completed week. Artist entry and exit labels require adjacent completed observations.

The live series uses [ListenBrainz sitewide artist statistics](https://listenbrainz.readthedocs.io/en/latest/users/api/statistics.html) with `range=week` for the immediately previous complete week and `range=this_week` for the current incomplete week. These named ranges are **not** arbitrary historical addresses. The collector validates their `from_ts`, `to_ts`, `range`, and `last_updated` against the expected UTC weeks and does not publish a previous week whose last source calculation predates its end. A current week shows its entire calendar range but its exact last included listen timestamp is not exposed. The interface prints the last source calculation time and a freshness phrase in days since that calculation; this timestamp is **not** the event cutoff. No elapsed-day percentage is computed because the verified cutoff is unavailable. Repeated daily collection does not create additional weekly slots; it updates the same week only when counts or the explicitly labeled reference graph change. A partial slot is replaced with a complete result when it becomes the verified previous week. The API archives are actual captured source results, not interpolated or backfilled rankings.

**2026 availability as of September 25:** W38 (September 14–20) complete, W39 (September 21–27) partial; W01–W37 missing. W40–W53 have not occurred yet. The partial week cannot be compared to a complete week as a like-for-like change. With only one complete week, Play is disabled and explains why. Later dates and weeks appear only when collected or processed from a verified full dump.

The ranking population is ListenBrainz sitewide submitted listens with identifiable MusicBrainz artist IDs (MBIDs). Fetch 300 public chart rows to obtain 100 unique identified artists. Exclude missing MBIDs without guessing identities; for duplicate MBIDs retain the largest row without summing. Sort by descending `listen_count`, then MBID for ties, and assign ranks 1–100. Distinct listener counts are not available in the API chart. Artist IDs are stable across weeks; an artist outside the top 100 is **unknown here**, not zero listens. The name comes from the chart and can be flagged when missing. No Spotify follower ranking is used.

## Three different measures

**Recorded activity.** The circle radius, in map units, is `5 + 27 × sqrt(c / (c + 25,000))` for weekly recorded listens `c`. This fixed, saturating scale prevents an exceptional artist from swallowing the rest. **Circle area is not proportional to listens.** Exact count and rank appear on selection. Circle position, size, color and opacity interpolate for about one second only between adjacent completed weeks; every intermediate frame is drawing, not another measurement. Entering artists grow in and departing artists fade out. Choosing a partial week or a gap switches directly to that state, without a misleading count transition. When reduced motion is enabled, the map moves directly to the measured state.

**Audience affinity or overlap.** In the live API series, `weekly_edges=[]` and `weekly_relationship_status=unavailable_from_aggregate_stats`. The visible optional `reference_edges` come from ListenBrainz Labs' [similar-artists session index](https://labs.api.listenbrainz.org/similar-artists), requested at collection time. It is a *nonweekly reference*. It does not return a complete same-week shared-audience intersection, its observation horizon does not match the chart, and its index refresh timestamp is not supplied. Our `retrieved_utc` records retrieval time only. For seed artist `i`, define `M_i` as its largest returned session score across all results. For pair `i,j`, define `S_ij` as the maximum directed result among the two directions. The reference strength is `min(1, S_ij / sqrt(M_i M_j))` where both maxima exist. Duplicate directional rows are never added. Keep up to 120 reference pairs in the weekly file; the map draws at most 65 strongest pairs and limits ordinary degree to four. Selecting an artist shows up to nine closest links. Louvain communities (NetworkX 3.4.2, weighted, resolution 1, fixed seed 42) and a seeded spring layout use this reference graph in the API series. They are **algorithmic neighborhoods**, not genres, an artist's followers, or a measured weekly audience-overlap graph. Community captions use an ID and artist count, never a representative artist as an owner. Previous coordinates and membership overlap stabilize consecutive snapshots. Lines may change when artists enter or leave the visible top 100 or when the separate index changes; this is not evidence of weekly user movement.

In a verified full-dump batch series, if every usable listen in the week has a user key, weekly overlap can be measured. For artist `i`, let `c(u,i)` be user `u`'s listens to that artist in the fixed week. The weighted Jaccard similarity is `sum_u min(c(u,i),c(u,j)) / sum_u max(c(u,i),c(u,j))`, with zero counts for users who listened to only one artist. The denominator equals `T_i + T_j − sum_u min(...)`, where `T` is the weekly artist total. An edge appears only for a pair with at least **10 shared users**, and only the 250 strongest are retained. If any credited listen lacks a user key, **the entire week's weekly audience graph is withheld**; counts can still be published. This graph is a property of the stated dump-derived population and week, never silently mixed with the live API reference index. A missing edge may also result from the 10-user publication threshold or the 250-edge display cutoff.

**Listener movement.** No directional transition or particle is currently published. Affinity and changes in chart counts do not identify the same users moving between artists. Even a full-dump weekly audience graph only says users listened to both artists *within* one week. A later migration method would choose each eligible user's primary artist in each of two complete adjacent weeks by highest count (tie by MBID), count changed pairs across the **same** users, and publish aggregates after privacy suppression; that method and its eligible cohort would need their own versioned field and review. The present `movement.status=unavailable` and empty `observed_transitions` are intentional. Line clicks give a precise connection description, with no arrow.

## Offline historical backfill

The official [ListenBrainz full listens dump](https://listenbrainz.readthedocs.io/en/latest/users/listenbrainz-dumps.html) contains time-stamped events broken down into year/month `.listens` JSON lines. The September 15, 2026 full listens archive was [listed at about 229 GB compressed](https://ftp.musicbrainz.org/pub/musicbrainz/listenbrainz/fullexport/listenbrainz-dump-2663-20260915-000002-full/). The same listing includes a 20 GB statistics archive, but its documented contents do not prove that it has complete arbitrary past-week sitewide artist counts under the API chart definition; it is not used as an unverified shortcut. The 229 GB archive is publicly listed with a checksum and does not require user OAuth, but direct fetches from this execution environment returned a Site Unavailable page. This workspace has about 29 GB free, so it cannot store that archive, let alone its private aggregation database. At 100 MB/s, merely reading 229 GiB twice for the SHA-256 check and compressed scan takes about 1.4 hours; JSON parsing, SQLite aggregation, and audience intersections can take many more hours. This is a lower bound, not a runtime guarantee. **No historical backfill ran here.**

It is feasible on a dedicated batch host with substantial storage and time, not inside a routine Pages build. Full archives are preferable to stitching incrementals: ListenBrainz documents that deletions do not appear in incremental dumps until the next full import. Backdated imports and changing mappings can also revise historical statistics. Historical dump counts will not necessarily reproduce a prior API chart calculation; they remain a separate series and state their population and processing date. An archive captured September 15 cannot verify later weeks, including W38 and W39. A later full dump would be needed for a longer 2026 series.

1. On a private batch machine, run `python collector/backfill.py --preflight --expected-archive-bytes <official-byte-size> --workdir /private/scratch`. This checks local free scratch space against a conservative minimum of one compressed-archive size for the temporary database, plus the presence of `zstd`; actual database needs can be higher. Download an official full `listenbrainz-listens-dump-…tar.zst` and its published SHA-256 checksum; install the Python packages in `collector/requirements.txt`. Re-run preflight with `--archive /private/archive.tar.zst` so the local size is measured. The archive and scratch volume may be separate.
2. Run `python collector/backfill.py --archive /private/archive.tar.zst --sha256 <published-64-character-digest> --archive-id <published-id> --captured YYYY-MM-DD --year 2026 --workdir /private/scratch`. The program verifies the archive digest, streams monthly JSON lines, checks that all months covering each complete week are present, and aggregates only complete ISO weeks at or before the archive capture date. A week with fewer than 100 identified artists remains missing. It rejects a missing month rather than treating it as zero activity.
3. The private temporary SQLite database stores keyed one-run hashes of user names for audience intersections, not raw user names. It is deleted at the end of the batch. The published files contain only aggregate counts, ranks, MBIDs, similarity scores, and shared-listener counts for pairs of at least 10 users. No raw event, user key or archive is copied into `public/`.
4. Run `python collector/validate_weekly.py public/data/weekly-dump/manifest.json`, which checks ISO boundaries, unique artist IDs and ranks, source capture after week end, quality counts, privacy threshold, and snapshot content digests. Inspect quality flags, population, provenance, and archive capture time, then commit only the compact `weekly-dump` output. The website then offers a separate **Historical full dump** series selector. It does not splice dump-derived weeks into the API chart series. A later full archive may replace the backfill series after rerunning and checking corrections.

The processor credits one listen once to each *distinct valid* artist MBID in the event's `artist_mbids`. It prefers ListenBrainz server-resolved `mbid_mapping.artist_mbids` when present; otherwise it uses client-submitted `additional_info.artist_mbids`, whose correctness is **unverified** even if their UUID shape is valid. The count of fallback rows is published as `client_submitted_id_rows` for review before release. It excludes missing or invalid MBIDs, never guesses from a text artist name, and deduplicates repeated MBIDs within one event. Server-resolved artist credit names are preferred when available. Names attached to multiple-artist events without individual credits are not assigned to an artist; an MBID fallback name is flagged `name_unverified` until metadata is independently resolved. It does not silently deduplicate two apparently identical listens at the same second, because those may be legitimate repeated plays. It reports missing IDs and missing user keys. These choices differ from the API's precomputed mapping and are why the series are not merged. Full dump user histories may be publicly downloadable, but no username, persistent pseudonym or raw history is included in this static site.

## Schema v3 and operations

`public/data/weekly/manifest.json` has `schema_version: 3`, `series_id: sitewide_stats_api`, `default_year: 2026`, and `years[year].weeks[]`. Each entry has an ISO `id`, inclusive `start`, exclusive `end_exclusive`, `status`, and, for observations only, `path`, `signature`, and source calculation time. The optional `weekly-dump/manifest.json` has a separate `series_id` and the same week-slot shape. Each compact `YYYY-Www.json` includes:

| Field | Meaning |
| --- | --- |
| `week_id`, `start`, `end_exclusive`, `status` | Exact UTC ISO period and complete/partial state. |
| `source.kind`, `range`, `population`, `last_calculated_utc`, `captured_utc` | API provenance and freshness; dump files use archive ID, SHA-256 and capture date instead. |
| `artists[].id`, `name`, `listen_count`, `rank`, `distinct_listener_count`, `quality_status` | MBID, displayed name, exact recorded listen credits, unique rank, unavailable distinct listeners, identity caveats. |
| `artists[].cluster_id`, `x`, `y` | Algorithmic community ID and normalized stable display coordinates. |
| `weekly_edges[]`, `weekly_relationship_status` | Empty in API snapshots; weighted Jaccard pairs only when a complete dump week supports them. |
| `reference_edges[]`, `reference.matches_week` | Nonweekly session-affinity reference in API snapshots only; `matches_week=false`, no shared-listener counts. |
| `movement.status`, `observed_transitions` | Always unavailable and empty in v3. |
| `quality` | Excluded rows, duplicate source MBID rows, and dump input limitations. |

The workflow fetches only `week` and `this_week` at 06:17 UTC each day. Invalid boundaries, stale previous-week calculations, malformed payloads and validation failures prevent new publication while leaving the last deployed site intact. The static frontend fetches a small manifest and lazy loads per-week JSON; it preloads the next observed week. Search and detail history load additional available weeks on demand. The Pages site never receives source access tokens or raw histories. A week remains missing until an authorized documented source actually reconstructs it.
